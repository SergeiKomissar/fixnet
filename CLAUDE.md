# CLAUDE.md — контекст проекта fixnet

Этот файл читается Claude Code при открытии проекта. Здесь — суть инструмента,
диагноз, принятые решения и то, что сознательно НЕ делается. Цель: чтобы при
доработке не предлагались уже отвергнутые варианты.

## Что это

`fixnet.sh` — аварийная кнопка восстановления интернета на macOS (Apple Silicon).
Чинит ситуацию, когда после переключения/обрыва VPN или моргания сети интернет
пропал и сам не вернулся. Запускается кликом по иконке `fixnet.command` в Dock
(или из терминала). Целевой пользователь — владелец машины, не сисадмин.

Окружение: MacBook M4, macOS (русифицированная), zsh. Выход в сеть — Wi-Fi или
раздача с iPhone (оба через `en0`). Три VPN: два коммерческих full-tunnel
(Hide My Name, ExpressVPN, используются по очереди) + Tailscale (split, для серверов).

## Диагноз (честный, без завышенной причинности)

Наблюдаемая поломка: после переподключения VPN пропадает IPv4 default route,
связь не восстанавливается сама. Рядом копятся IPv6-дефолты на мёртвых utun.

ВАЖНО: прямая причинность «IPv6 utun блокируют IPv4 DHCP» НЕ доказана. Скорее
обе проблемы — следствие некорректного завершения VPN-сессии через
NetworkExtension. Реально лечит ситуацию пересборка маршрутов + DHCP renew, а
не охота за туннелями. Поэтому скрипт чинит мягко и адресно.

## Архитектура решения

1. `detect_iface` — определяет физический uplink. Приоритет: интерфейс из
   текущего default route (если это enX, а не utun) -> Wi-Fi-сервис (по «Device:
   enX», устойчиво к локали) -> первое active en -> фолбэк en0.
2. `check_net` — два внешних IP (1.1.1.1 / 8.8.8.8), любой ответ = связь есть.
3. `check_dns` — ЖИВОЙ резолв через dig/nslookup/host (НЕ кэш dscacheutil!),
   два домена (ya.ru / apple.com), реальные имена (не случайный поддомен).
4. `locate_break` — локализатор обрыва по звеньям (IP -> шлюз/VPN -> интернет ->
   DNS). Возвращает код причины (noip/gateway/uplink/vpndns/route/unknown),
   который РЕАЛЬНО управляет дальнейшим решением.
5. Развилка по причине:
   - uplink (источник лёг) -> честный выход, маршруты не трогаем;
   - gateway (шлюз молчит) -> одна осторожная попытка передёрнуть Wi-Fi, выход;
   - vpndns -> двухступенчатая починка DNS (мягкий HUP, затем жёсткий перезапуск
     mDNSResponder — то, что делает перезагрузка, но без неё);
   - route/noip/unknown -> полная починка (Ступени 1-2).
6. Ступень 1: route flush -inet + прицельное удаление IPv6-дефолтов на utun +
   DHCP + сброс DNS. Ступень 2: передёрнуть Wi-Fi (только если это Wi-Fi).

Режим `--check` — диагностика без починки и без root.

## Companion: netinfo.sh (диагностика, не ремонт)

`netinfo.sh` — отдельная read-only утилита «осмотра» рядом с «ремонтом».
Состояние системы НЕ меняет (только смотрит). Root НЕ обязателен, но кнопка
запускает через sudo РАДИ ТОЧНОСТИ (под root виден флаг скрытой сети). Отвечает
на боль «при слабом VPN непонятно, есть интернет или нет и где я»: крупный ИТОГ
сверху (🟢/🟡/🔴) + подробности.

ПРИНЦИП ПРИОРИТЕТОВ (со слов владельца): главное — ТОЧНОСТЬ, а не «без root».
Это личная машина; ради точных данных root допустим. Не путать с fixnet, где
суть в безопасности правок.

Вывод ДВУХРЕЖИМНЫЙ. По умолчанию — ЧЕЛОВЕЧЕСКИЙ язык без жаргона (владелец, не
сисадмин — см. «Что это»): «Подключение: Wi-Fi», «Интернет: есть (задержка 9 мс
— отлично)», «Скорость ↓/↑ … — нормально», «Нас видят из: Страна, Город»,
мягкое замечание про «следы старых VPN». Технический срез (интерфейс, default-
маршрут, utun, DNS-серверы, RTT) — по флагу `--tech`. Это осознанное решение по
прямой просьбе владельца: НЕ возвращать жаргон в дефолтный вывод.

ВЕРДИКТ 🟢 ОПИРАЕТСЯ НА HTTPS, А НЕ НА ICMP (правка по внешнему ревью). Главный
критерий «интернет работает» для человека — открываются ли сайты (HTTPS 443) +
жив DNS, а не проходит ли ping. ping может идти при зарезанном 443 (captive
portal, корпоративная сеть, кривой VPN, блокировка TLS/прокси) — это НЕ 🟢, а 🟡
«пинг и DNS есть, но сайты не открываются». НЕ возвращать вердикт на `NET` (ICMP).
check_dns спрашивает A и AAAA отдельно (устойчивее к CNAME-цепочкам в dig +short).
Пороги speed_word сдвинуты под VPN: <2 очень медленно, <8 медленно, <25 нормально,
<80 быстро, иначе очень быстро (для далёкого VPN 11 Мбит/с — это «нормально»).
🔴 ГРАБЛИ (поймано вживую, РФ без VPN): `to_mbps` возвращал `"0"` при крошечном (частичном/
заблокированном) трансфере → вывод «0 Мбит/с — очень медленно» при ОТКРЫВАЮЩИХСЯ сайтах (ложь:
0 Мбит/с при рабочих сайтах = недостижим эндпоинт скорости speed.cloudflare.com, а не реальная
скорость). Лечение: `to_mbps` отдаёт ПУСТО при результате <0.5 Мбит/с (округляется в 0) → срабатывает
честная ветка «замер не удался»; при живых сайтах добавляем «(сервер скорости недоступен из этой
сети?)». Пустой DL_M не тащит вердикт (нет «низкая скорость 0»), не даёт ложное «узкое место», в JSON
download_mbps=null. Реальные ≥0.5 Мбит/с показываются как и раньше (0.8→1, 15→15).

ФАЗА 15.2 — FALLBACK speed-эндпоинтов (универсальный, не «российский»): СКАЧИВАНИЕ пробуем
Cloudflare → CacheFly → OVH (РАЗНЫЕ CDN), берём ПЕРВЫЙ валидный (≥0.5 Мбит/с). Закрывает слепое
пятно «скорость зависит от доступности ОДНОГО сервера» (из РФ без VPN Cloudflare-эндпоинт не
отвечал). Бюджет времени: primary 20с, fallback по 12с; не доходит до fallback, если primary дал
результат. ОТДАЧА — только Cloudflare (надёжного анонимного POST-приёмника для fallback нет) →
при провале честно «замер не удался». В человеческом выводе метку источника показываем ТОЛЬКО при
fallback («N Мбит/с — нормально (запасной сервер)»); в --tech всегда строка «сервер скорости:
cloudflare | cachefly (запасной) | …». SPEED_SRC="" если замер не удался. 🔴 ГРАБЛИ: сперва паковал
флаги curl в строку и полагался на word-splitting `$_opt` — в ZSH неквотированная строка НЕ
разбивается на слова → curl получал один кривой аргумент, fallback «не работал». Лечение: флаги
задаём ЯВНО per-endpoint (case по метке), без упаковки — надёжно в bash/zsh/sh. Эндпоинты
грунтанул вживую: cloudflare/cachefly/ovh отдают 206/200 + octet-stream + Range; мок с битым
primary → выбран cachefly. НЕ Ookla: нужен грубый индикатор канала, не идеальный speedtest.

ФАЗА 15.3 — детектор `manual_dns_private_mismatch` (диагноз корня DNS-сбоя, read-only). РЕАЛЬНЫЙ
КЕЙС владельца: в сервис «Wi-Fi» вручную вписан DNS `192.168.5.1` (домашний роутер). macOS применяет
DNS Wi-Fi ко ВСЕМ Wi-Fi-сетям (включая раздачу телефона) → дома адрес живой, на раздаче/в отеле
мёртвый → имена не резолвятся (DoH идёт мимо). `wifi_manual_dns_mismatch`: режим Wi-Fi-DNS = manual
И адрес приватный (192.168/10/172.16-31) И НЕ на текущей подсети (первые 3 октета ≠ LOCAL_IP) →
возвращает адрес. `print_dns_repair`: при совпадении советует КОРЕНЬ — `sudo networksetup
-setdnsservers Wi-Fi Empty` (вернуть автоматический; дома DHCP сам выдаст роутер, на раздаче — DNS
оператора), а `fixnet --dns` как разовый обход СИМПТОМА. 🔒 Точный, не шумит: дома (та же подсеть) /
публичный DNS (1.1.1.1) / автоматический → не срабатывает; только при DNS=0 + приватный-чужой-подсети.
Медиасерверы владельца идут через Tailscale MagicDNS (100.100.100.100 → *.ts.net), от 192.168.5.1 НЕ
зависят → Empty их не ломает. netinfo только СОВЕТУЕТ (read-only), DNS не меняет. Юнит-тест 4 кейса ✅.

ПРАВКИ ПО ВНЕШНЕМУ РЕВЬЮ (Manus + Gemini, две независимые проверки). Внедрено
согласованное; спорное (параллелизация) и отклонённое (мониторинг, история,
сравнение замеров, DNS-leak) — НЕ делаем:
  - CAPTIVE PORTAL: HTTPS-коды СТРОГО (204 для generate_204, 200 для apple; 30x
    больше НЕ считаем за «работает» — это давало ложное «сайты открываются» за
    порталом). Отдельная проба `curl -sL http://captive.apple.com/hotspot-detect.html`:
    тело не «Success» -> CAPTIVE=1 -> вердикт «🟡 НУЖНО ВОЙТИ В СЕТЬ».
  - VPN-ДЕТЕКТ по маршруту до ВНЕШНЕГО IP (`route -n get 1.1.1.1` -> utun*), а не
    по default route: ловит сплит-дефолт (0.0.0.0/1+128.0.0.0/1) у OpenVPN/
    WireGuard/Tailscale, который сам default route не трогает.
  - GEO-ФОЛБЭК строго по HTTPS (`ifconfig.co/json`, поле country_iso = КОД страны,
    как ipinfo). HTTP ip-api убран: по HTTP captive вернул бы HTML и утёк бы IP.
    json_get теперь через python3 (надёжнее sed к минификации), sed — фолбэк.
  - ДЖИТТЕР (stddev) и ПОТЕРИ пакетов из одного `ping -c5`: входят в «Для VPN»
    (потери ≥10% -> 🔴; джиттер >30 «сильный», >10 «плавает»; потери >0 -> минус)
    и показываются (строка «потери» в человеческом, джиттер/потери в --tech).
  - ПОРОГ utun поднят: норма ≤4 (macOS штатно держит 3–4 для AWDL/Handoff/
    Tailscale), «есть» >4, «много» >7 — иначе ложная тревога на чистой системе.
  - АНТИ-ANSI-ИНЪЕКЦИЯ: SSID и поля geo чистим `clean()` (tr -d cntrl + trim) —
    вредная сеть с escape в имени не сможет управлять терминалом; trim заодно
    чинит совпадение SSID в wifi_hidden. SSID/SEC сбрасываются в начале collect_all.

МЕНЬШЕ СПОРНЫХ ВЫВОДОВ (правка по ревью — сетевой скрипт теряет доверие, если
обвиняет VPN, которого нет, или зовёт Tailscale «выключенным VPN»): (1) строка
«VPN-выход: не обнаружен» (НЕ «VPN выключен»): Tailscale split-VPN может быть
активен, но не менять внешний IP — full-tunnel-выхода нет. (2) «Для VPN»
чувствительно к ДЖИТТЕРУ, не только к avg: разброс RTT (max-min) >50 → «задержка
плавает», >100 → «сильный разброс»; зелёный только при RW≤80 И spread≤50 И
скорости≥8. (3) «узкое место» НЕ упоминает VPN, если VPN-выхода нет → «ограничение
дальше по цепочке»; список (провайдер/хотспот/маршрут) ушёл в advice. (4) advice
при выключенном VPN ведёт с «включи VPN», а не «смени сервер» (сервера ещё нет);
ветка открытая+VPN-выкл идёт ВЫШЕ ветки «узкое место». (5) --tech: «Tailscale DNS:
обнаружен» при 100.100.100.100 / fd7a:115c:a1e0; пометка к link rate «ниже
ожидаемого», если он мал при отличном RSSI и канале ≥80 МГц; примечание, что
качество считается по внешнему RTT/HTTPS/скорости, а RTT шлюза — справочный.
Timestamp замера — СВЕРХУ (перед «Качество»), чтобы свежесть была видна сразу.

ДОВЕРИЕ К ДИАГНОЗУ (правка по ревью, не новые функции — меньше шума, больше веры
цифрам): (1) TIMESTAMP замера — collect_all пишет STAMP/STAMP_SHORT; в обычном
выводе «Замер: HH:MM:SS (r — обновить)», в --tech полная дата. Чтобы при висящем
окне было ясно, свежие ли данные. (2) RTT min/avg/max + СТАБИЛЬНОСТЬ (rtt_stats по
5 пакетам, разброс max-min): для VPN дрожащий пинг важнее среднего. Суффикс к
задержке: ≤30 ровно, ≤80 «плавает», иначе «нестабильно». В --tech «RTT наружу:
min/avg/max». (3) RTT до ШЛЮЗА — только справочно с пометкой «ICMP к роутеру
непоказателен» (роутер может медленно пинговаться, но нормально маршрутизировать;
видели 603 мс к шлюзу при 13 мс наружу). НЕ использовать RTT шлюза как качество.
(4) Строка «узкое место»: если сигнал Wi-Fi отличный (RSSI≥-60), а скорость <15 —
причина НЕ в радио (провайдер/хотспот/VPN/маршрут). Сильно повышает ценность.
(5) Разделители divider() между экранами t/a/r. (6) Порог utun мягкий: >6 «много»,
>2 «есть». render_advice приоритезирован по ПРИЧИНЕ: слабый сигнал → узкое место
(Wi-Fi ок, но медленно) → открытая+VPN-выкл → VPN-вкл → общий.

ПРОГРЕСС-СПИННЕР (правка по UX — «тихое ожидание» читалось как зависание). Общий
`nl_spin_start/nl_spin_stop` в netlib крутит «живой» индикатор с подписью текущего
шага во время ДОЛГИХ операций (замер скорости, geo, RTT, MTU-зонд, `wait_net`).
Грабли учтены: (1) пишем в `/dev/tty`, а НЕ в stdout — иначе засорили бы пайпы/логи
и попали бы в `$(...)`; (2) анимация только в живом терминале (`[ -t 1 ]`), в пайпе
no-op; (3) кадры Braille — МАССИВОМ `NL_SPIN_FRAMES`, а не срезом строки `${s:i:1}`:
на bash 3.2 срез многобайтных символов их бьёт; (4) `trap nl_spin_stop EXIT INT TERM`
в обоих скриптах — не оставить процесс/строку (через единый `cleanup()`, чтобы
будущие хуки не плодили новые trap и не перетёрли этот; откат DNS/MTU — НЕ в trap,
он на файле+self-heal). Флаги: `NL_NO_SPINNER=1` — без анимации (SSH/сухой вывод);
`NL_SPINNER_STYLE=ascii` — кадры `| / - \`, если Braille в терминале квадратиками;
`nl_spin_ok` проверяет `NL_NO_SPINNER` + `[ -t 1 ]` + `[ -w /dev/tty ]`. netinfo:
`ni_step "label"` = шаг N/M
(стоп прошлого + старт нового) в collect_all; в конце collect_all `nl_spin_stop`
перед печатью отчёта (рендеры печатают чисто). fixnet: `wait_net_spin` (обёртка
вокруг wait_net, возвращает её код для `if`) + спиннер на nl_path_mtu.

АРХИТЕКТУРА «СБОР → РЕНДЕР» (правка по ревью, важно). Все измерения (ping/speed/
geo/RSSI) делаются ОДИН раз в функции collect_all(); render_human/render_tech/
render_advice только печатают уже собранное. Интерактивное меню (внутри скрипта,
не в .command!): `t` детали, `a` советы, `r` обновить замер, Enter закрыть. t/a НЕ
пересобирают данные — иначе на соседних экранах прыгали бы цифры и терялось доверие
(именно этот баг был, когда меню жило в .command и каждое нажатие = новый запуск).
Пересобирает только `r`. Меню показываем лишь при выводе в терминал (`[ -t 0 ]`),
иначе (пайп/одиночный --tech/--advice) — без меню. render_advice КОНТЕКСТНЫЙ:
VPN выкл+сеть открытая → «включи VPN…»; VPN вкл → «если тормозит…»; иначе общий
совет про канал. Блок «Для VPN» (не «Работа через VPN» — чтобы не читалось как
«VPN уже работает»). utun в человеческом выводе — «N туннелей», слово utun только
в --tech. Сигнал показывает и ширину канала (МГц) — для скорости важнее номера.

ТРИ УРОВНЯ ВЫВОДА (правка по ревью — обычный режим не должен быть мини-инструкцией):
обычный = короткий диагноз + ОДНО действие; `--advice` = + подробные советы «если
VPN тормозит»; `--tech` = технические детали. Длинный список советов в обычном
режиме показываем ТОЛЬКО когда VPN реально активен и качество не 🟢 (иначе был бы
казус «VPN выключен, а советы про тормозящий VPN»); если канал так себе, но советы
спрятаны — короткий указатель «netinfo --advice». city_name() переводит частые
города (Istanbul→Стамбул). short_org() для «Turk Telekom» — отдельный кейс (общий
срез превратил бы «Turk Telekomunikasyon» в «Turk»). Вторая строка вердикта
короткая («🟡 ОТКРЫТАЯ WI-FI СЕТЬ»), объяснение — в строке ВЫВОД. VPN определяем
ПО ФАКТУ (default route на utun), не по geo/IP; выключен — нейтрально «похоже,
выключен». Блок «Работа через VPN» (не «Качество для VPN»): при выкл. VPN это
«пригодна ли сеть», при вкл. — «как ведёт себя VPN». Кнопка netinfo.command
заканчивается `read` (Enter), чтобы итог не сменялся служебными строками logout.

ПОДАЧА ЧЕЛОВЕЧЕСКОГО РЕЖИМА — «диагноз», а не список измерений (правка по ревью).
Порядок смысла: можно ли работать → почему → что делать. Конкретно:
  - Верхний вердикт ДВУХСТРОЧНЫЙ: MAIN (🟢 ИНТЕРНЕТ ЕСТЬ / 🟡 … / 🔴) + отдельная
    строка SECURITY (🟡 СЕТЬ ОТКРЫТАЯ) — риск открытой сети не прячем в середину.
  - Внутренние статусы-переменные: MAIN_OK, SEC_OPEN, VPN_ACTIVE, QLEVEL, WORK.
  - Строка ВЫВОД (WORK) — синтез решения («можно работать; сеть открытая — включи
    VPN» и т.п.). Это и отличает утилиту от набора ping/curl/ifconfig.
  - Гео по-человечески: country_name() (TR→Турция), short_org() (срез AS-номера и
    юр. суффиксов: «Turk Telekom…»). Код страны и полный AS-провайдер — в --tech.
  - VPN-выход: тревожную строку «не та страна» показываем ТОЛЬКО при VPN_ACTIVE
    (default route на utun); иначе нейтрально «VPN-выход: не обнаружен».
  - utun-следы: не пугаем, даём действие («закрой VPN-клиенты и перезагрузи»).
  - speed_word: <8 Мбит/с теперь «терпимо» (не «медленно») — для VPN это рабочее.

СИГНАЛ Wi-Fi (честно о границах). Показываем RSSI (dBm) + качество (rssi_word) +
SNR + диапазон/канал. Источники: диапазон/канал — `system_profiler` (без root);
RSSI/шум/Tx Rate/MCS/PHY — `wdutil info` (ТОЛЬКО под root; поля сверены вживую:
«RSSI : -46 dBm», «Noise», «Channel : 5g100/80»). Без root показываем лишь
диапазон/канал + «силу покажет кнопка/sudo». Цвет уровня: ≥-67 зелёный, ≥-75
жёлтый, иначе красный; при <-67 — подсказка «ближе к роутеру». ПРИНЦИПИАЛЬНО НЕ
делаем (не врать): «метры до роутера» (RSSI→метры неточно: стена = как 10 м) и
любое программное «усиление сигнала» (это физика: мощность роутера/антенны/стены,
софт не меняет). netinfo только МЕРЯЕТ и СОВЕТУЕТ (двигаться/5 ГГц/меньше помех);
усиление невозможно, поэтому не предлагать «boost wifi». Диагностическая ценность:
сигнал отличный + скорость низкая => Wi-Fi ни при чём, причина дальше (провайдер/VPN).

ОЦЕНКА «КАЧЕСТВО ДЛЯ VPN» (синтез, человеческий режим). Отдельно от верхнего
итога: верхний итог = «могу ли в браузер» (по HTTPS+DNS), а «Качество для VPN» =
«годится ли для туннеля/видеосвязи» (по доступности + ЗАДЕРЖКЕ + скорости).
🔴 если сайты/DNS не работают ИЛИ RTT>180; 🟡 если RTT>90 или скорость<8 Мбит/с;
иначе 🟢. При не-🟢 печатаем практические подсказки (ближе к роутеру/5 ГГц —
только для Wi-Fi; другой VPN-сервер/протокол OpenVPN TCP 443/Lightway/IKEv2;
выключить лишний VPN/Tailscale; iPhone по USB). ПОЧЕМУ так: чужому роутеру нельзя
«приказать» дать приоритет (QoS/WMM/DSCP у клиента он почти всегда игнорирует) —
поэтому НЕ просим приоритет, а оцениваем сеть и советуем. Блок показывается только
при наличии связи (иначе всё уже сказал верхний итог).

🔴 macOS 26/SEQUOIA ПРЯЧЕТ SSID (важно, поймано вживую по скрину владельца): на macOS 15+/26
`system_profiler SPAirPortDataType` и `ipconfig getsummary` отдают SSID/BSSID как ЛИТЕРАЛ
`<redacted>` приложениям БЕЗ доступа к Службам геолокации (проверено: system_profiler даёт 12×
«redacted», ipconfig — «SSID : <redacted>»). Это ОС, НЕ наш код (grep «redact» по проекту пуст).

🔴 ПОПЫТКА ВЕРНУТЬ ИМЕНА ПРОВАЛИЛАСЬ (проверено вживую, не теория): Терминала НЕТ в списке Служб

нет — это отправляло на бесполезный квест), а пишем «имя скрыто macOS (приватность; вернуть из CLI
обычно нельзя — на диагностику не влияет)».

Имя Wi-Fi (SSID) берётся из `ipconfig getsummary` (надёжно, без геолокации,
устойчиво к локали) — показываем даже для СКРЫТЫХ сетей, которые macOS в меню
прячет за «Небезопасная скрытая сеть». Пометки безопасности сводятся в один хвост
«(скрытая, без пароля ⚠)»:
  - «без пароля» — из `Security: NONE` (надёжно, без root);
  - «скрытая» — из флага `Hidden:bool` в `/Library/Preferences/com.apple.wifi.
    known-networks.plist` (читается ТОЛЬКО под root). Структуру сверили вживую:
    ключ записи `wifi.network.ssid.<SSID>`, внутри `SSID:bytes` (по нему, с NFC-
    нормализацией, сопоставляем текущую сеть) и `Hidden:bool`. Парсит python3
    (см. wifi_hidden). `wdutil info` скрытость НЕ отдаёт (проверено).
ГРАНИЦА ТОЧНОСТИ (важно, проверено вживую): флаг «скрытая» есть только для
СОХРАНЁННЫХ сетей. Если сеть подключена без сохранения — её в known-networks нет,
и мы ЧЕСТНО МОЛЧИМ (не гадаем). Так было у владельца: текущая сеть оказалась
незапомненной открытой+скрытой, в plist отсутствовала; решено лучше не показать,
чем показать наугад (живой скан скрытости требует Геолокации и ненадёжен).
Без root «скрытая» тоже не показывается. Поэтому кнопка идёт через sudo.
Выбор владельца: приоритет — ТОЧНОСТЬ; ради неё sudo на кнопке допустим, а
недостижимый-надёжно сигнал лучше не показывать вовсе.

Сознательно разделены: fixnet чинит (root, меняет сеть), netinfo только смотрит.
Решение принято осознанно — НЕ предлагать слить их обратно в один скрипт.

Делает запросы НАРУЖУ (geo-сервис ipinfo/ip-api с фолбэком, HTTPS-проба 443) —
это осознанный компромисс ради geo; отключается флагом `--no-geo`.
Замер скорости (приём + передача, ~5 МБ в каждую сторону через Cloudflare
__down/__up) идёт ПО УМОЛЧАНИЮ — это ядро утилиты, без него непонятно, тормозит
ли канал. Решение принято по прямому требованию владельца, осознанно перевесив
риск платного трафика на раздаче iPhone; для этого случая есть `--no-speed`.
НЕ предлагать убрать скорость обратно за флаг.
Хелперы detect_iface/check_dns намеренно продублированы из fixnet.sh ради
самодостаточности — при правке правила интерфейса синхронизировать оба файла.

## Развитие в «швейцарский нож»: ТРИ СЛОЯ (закреплено)

Цель — оживлять интернет в любых условиях, НЕ размывая границы:
  - netinfo — НАБЛЮДАЕТ, измеряет, пишет СВОЮ локальную историю, открывает портал.
    НЕ меняет маршруты/DNS/Wi-Fi/MTU/VPN.
  - fixnet — РЕМОНТ: единственный, кто меняет сетевое состояние (root), с
    подтверждением и ПУЛЕНЕПРОБИВАЕМЫМ откатом (бэкап-файл + self-heal, не только trap).
  - shared state — `netlib.sh`: общий слой памяти/конфига/бэкапов; подключают оба
    (`. <dir>/netlib.sh`), источник правды по пути/владельцу/формату — только там.
Принцип: netinfo ставит диагноз → предлагает действие → fixnet выполняет с согласия.
Отклонено НАВСЕГДА (риск/ToS): авто-нажатие в captive-портале, интеграция с
проприетарными VPN-API (хранение секретов).

## Фаза 6 (сделано): link awareness + `netinfo --scan` (соседние Wi-Fi)

Цель — человек сразу видит, ЧЕРЕЗ ЧТО реально работает (Wi-Fi / раздача с телефона /
USB / кабель), и может глянуть соседние сети. БЕЗ попыток угадать то, чего macOS не
отдаёт. netinfo-only (read-only), fixnet НЕ участвует.

СТРОКА «Подключение» (основной вывод, ПОСЛЕ VPN-выхода — сначала «куда нас видит
мир», потом «через что физически идём»). Тип физического линка по IFACE (detect_iface
даёт enX, не utun → даже при активном VPN показываем РЕАЛЬНУЮ подложку, а не «через
utun» — для человека utun бесполезен, статус VPN и так строкой выше):
  - сервис `iPhone USB`/`iPad USB` (nl_service_for_device) → «iPhone/iPad по USB»;
  - Wi-Fi + IP `172.20.10.x` → «Раздача с телефона по Wi-Fi» (фикс-подсеть Apple
    Personal Hotspot — надёжный признак, не гадание; «iPhone/iPad» в названии ТОЛЬКО
    если видно из SSID, иначе нейтрально «телефон»);
  - Wi-Fi обычная → «Wi-Fi — «SSID»» + диапазон/канал/ширина ИНЛАЙН (band_human);
  - Ethernet/USB-LAN/Thunderbolt → «Ethernet / USB-LAN»; иначе «не определено».

5G/LTE СОЗНАТЕЛЬНО НЕ ОПРЕДЕЛЯЕМ (главный честный инвариант фазы). Mac физически НЕ
видит поколение сотовой сети айфона — при раздаче это просто IP-линк, ни поля, ни API
нет; по скорости тоже нельзя (5G бывает медленным, LTE быстрым, VPN/NAT искажают —
тот же запрет, что в «узком месте»). При раздаче (IS_HOTSPOT) печатаем ЧЕСТНУЮ
подсказку «5G/LTE с Mac не определяется — смотри на iPhone», и только при раздаче
(в обычном Wi-Fi не мозолит). НЕ возвращать определение поколения.

`netinfo --scan` — соседние сети (read-only, медленно → отдельный флаг + клавиша `s`
в меню, в обычном выводе только указатель «Соседние сети: netinfo --scan» при WIFI).
  - `airport -s` УДАЛЁН в новых macOS (на машине 26.5.1 — нет). Источник —
    `system_profiler SPAirPortDataType`, блок «Other Local Wi-Fi Networks» (PHY,
    Channel+band, Security, Signal/Noise). Парсит python3 по ОТСТУПАМ (вход в блок,
    запись = ключ на уровне entry, поля глубже; выход — отступ ≤ базового).
  - СИГНАЛ macOS отдаёт НЕ для всех сетей → где нет, честно «—» (не выдумываем).
    Сортировка: текущая первой → с сигналом по убыванию → без сигнала по имени.
  - «← вы здесь» метим лишь РАЗ (текущий SSID часто вещается на 2 диапазонах —
    оба совпали бы; метим сильнейший по сорту).
  - «открытая» ТОЛЬКО при явном `Security: None`; нет строки Security → «?», не
    «открытая» (не гадаем про отсутствие пароля). Открытые сети помечаем ⚠ и пишем
    «без VPN не для почты/банка/работы»; «лучший сигнал» советуем ТОЛЬКО среди
    защищённых. САМИ НЕ ПОДКЛЮЧАЕМСЯ (read-only + безопасность) — выбор в меню Wi-Fi.
  - Если скан пуст / без SSID → честно «нужна Геолокация для Терминала», не пустая
    таблица (на новых macOS скан соседей гейтится Службами геолокации).

🔴 ГРАБЛИ (стоили отладки): TSV между python и bash — **таб это IFS-whitespace**, и
ДВЕ подряд табы (пустое поле, напр. rssi) СХЛОПЫВАЮТСЯ в `read` → все поля съезжают
(iscur попадал в rssi, выходило «1 dBm» вместо «—»). Лечение: python ставит сентинел
`-` вместо пустых полей (нет подряд табов), bash возвращает `-`→пусто. Урок: при
`IFS=$'\t' read` НЕ допускать пустых полей между табами (или сентинел, или не-таб).

`--advice` при «Wi-Fi хороший, но медленно» (wifi_ok_slow): конкретные цифры (RSSI,
диапазон, канал) + причины + нумерованный список действий (netinfo --scan; при
раздаче — глянуть 5G/LTE на iPhone; сравнить без VPN; канал слаб для тяжёлого).

СМЫСЛОВОЙ ДВИЖОК (правка по ревью — был реальный баг). ИНВАРИАНТ: «включи VPN»
печатаем ТОЛЬКО когда VPN реально НЕ активен. Раньше WORK проверял SEC_OPEN раньше
VPN_ACTIVE → при открытой сети + активном VPN советовал «включи VPN», хотя сам же
показывал «VPN-выход: активен» (противоречие). Теперь WORK ветвится по ОБОИМ:
  - VPN активен + открытая → «VPN включён, риск открытой сети снижен{хвост качества}»;
  - открытая + VPN выкл → «сначала включи VPN»;
  - VPN активен → «VPN включён{, канал в порядке | хвост качества}»;
  - иначе → «можно работать{; ничего срочного | хвост}».
Хвост качества (QSUFFIX) единый: yellow «но канал медленный…», red «но канал
плохой — видеосвязь и большие загрузки…». render_advice так же VPN-aware: открытая
сеть → при активном VPN «риск снижает VPN, но не вводи пароли/платежи, если отвалится»,
при выкл. «сначала включи VPN». VPN-выход НЕ пугает «отвалился» (ожидаемую страну мы
не знаем): «активен — Страна, Город» + нейтральная строка «Проверка VPN: если ожидал
другую — сервер не тот». Память: «сеть знакомая — N замеров; прошлый — …». Узкий канал
(20 МГц на 5/6 ГГц) — заметка в --advice (объясняет низкую скорость при отличном сигнале).

## Фаза 13 (сделано): `netinfo --why URL` — на каком слое не открывается ресурс

ЦЕЛЬ: объяснить НЕ-сисадмину, на каком СЛОЕ ломается открытие конкретного ресурса
(сайт/файл/API/облако), и отделить «у меня сеть лежит» от «именно этот ресурс не идёт».
netinfo-only, read-only, БЕЗ ключей, систему НЕ меняет, fixnet не участвует. Отдельный
флаг (как --probe/--scan), в обычный вывод/JSON/меню не лезет.

ЦЕПОЧКА (всё переиспользование готового): требуем полный http/https URL (без схемы —
честный отказ с подсказкой) → host (IP-литерал DNS не требует — считаем разрешённым) →
КОНТРОЛЬ «сеть вообще жива» (HTTPS generate_204/apple) → DNS host (dig → doh_resolve
фолбэк) → ОДИН `curl -L --range 0-0 -o tmp -w '%{http_code}\t%{time_connect}\t
%{time_appconnect}\t%{content_type}'` → слой по exit+таймингам (tcp=0→TCP; tls=0&tcp>0→TLS;
есть код→HTTP) → классификация HTTP через `ai_classify` (регион/antibot/needs_key/451) +
файл-vs-HTML (`why_is_file` по расширению + Content-Type) → VPN как контекст (route на
utun, без geo). Тело — `head -c 8192` ТОЛЬКО для маркеров, в логи/вывод не кладём;
tmp с префиксом `netinfo-why.*` (cleanup чистит и его).

КЛАССЫ: local_network / dns_problem / dns_doh_only / tcp_blocked / tls_blocked /
http_forbidden(reason: регион|antibot|forbidden) / blockpage(блок-заглушка при 2xx) /
auth_required(401|needs_key) / html_instead_of_file / not_found(404) / rate_limited(429) /
server_error(5xx) / redirect_loop(3xx после -L) / slow_or_timeout / ok.

BLOCKPAGE (правка по живому РФ-кейсу, важно): региональный блок часто отдаётся СТРАНИЦЕЙ-
ЗАГЛУШКОЙ с HTTP 200 + text/html (Claude `app-unavailable-in-region`: «App unavailable —
Claude is only available in certain regions»), а НЕ кодом 403/451. range 0-0 (1 байт) этого
не видит → говорили «отвечает нормально». Лечение: для `text/html`/json/xml/plain ДОЧИТЫВАЕМ
до 16 КБ тела (вторым curl `-r 0-16383`, ТОЛЬКО HTML/текст — файлы pdf/zip/бинарь НЕ трогаем,
им пустое тело = ok по коду) → `ai_classify` ловит регион-маркеры даже при 200. Новый маркер
`region_restricted` («available in certain regions», «app unavailable in region», «not available
in your region»). При v=blocked И код 2xx → wclass=blockpage (а не http_forbidden): в «Проверки»
строка «Содержимое: страница-заглушка», в «Вывод» — «сетевые слои прошли, но прислал заглушку»
+ РЕГИОН и СТРАНА ВЫХОДА («выходишь из «Россия» (VPN выключен) — включи VPN»). Дисклеймер честно:
«файл не качаем, HTML читаем кратко (до 16 КБ) на маркеры блокировки» (НЕ «1 байт»). ОСТАТОЧНЫЙ
риск: блок-страница с НЕизвестной фразой проскочит как ok (маркеры пополняемы); ложный плюс на
обычной странице, случайно содержащей фразу-маркер, — возможен, но маркеры специфичны.
ФОРМУЛИРОВКА blockpage ДИФФЕРЕНЦИРОВАНА по block_reason (правка по ревью — не всякая заглушка =
именно блокировка; бывает продуктовая недоступность/policy/compliance/age-gate): antibot →
«антибот-/CDN-защита»; ЯВНЫЙ регион-маркер (region_restricted / *country not supported*) →
сильно «региональное ограничение: доступен только в некоторых странах»; иначе (`*)`) честно
«региональное ИЛИ политическое ограничение — не из всех стран/IP», без пережима. ⚠ В ДОКАХ/тестах
`claude.com/app-unavailable-in-region` — это тест РАСПОЗНАВАНИЯ заглушки (URL отдаёт её всем,
даже из рабочей страны), НЕ доказательство «Claude недоступен из страны X».

CURL ≠ БРАУЗЕР (важный инвариант, правка по живому ложному плюсу). `--why` стучится curl'ом —
БЕЗ cookie, сессии и JS. Поэтому страницы за входом / SPA-маршруты (напр. `claude.ai/new`)
и сайты за Cloudflare отдают пробе **403 «Just a moment…»** (JS-проверка Cloudflare), хотя в
залогиненном браузере с cookie+JS всё ОТКРЫВАЕТСЯ. РАНЬШЕ это давало ложное «антибот — смени
сервер». Лечение: отделяем Cloudflare-ЧЕЛЛЕНДЖ от ЖЁСТКОГО блока. ai_classify (по ТЕЛУ):
`cloudflare_challenge` ← «just a moment» / «checking your browser» / «verify you are human» /
«turnstile» / «enable javascript and cookies» (браузер проходит); `cloudflare_block` ←

## Фаза 14.1 (частично): таксономия сетевых ограничений в `--explain` + TLS/SNI в `--why`

ИСТОЧНИК ИДЕИ: внешняя статья-история блокировок (по слоям: DNS / IP-L3 / SNI-TLS / L7 / протокол
VPN / белый список). Берём как СЛОВАРЬ диагностических классов, НЕ как данные (там нет API/JSON).
СДЕЛАНО (безопасный текст, без новых проб): (1) `--explain` пополнен нейтральными пунктами — «Имя
сайта в TLS (SNI)», «Блокировка по адресу (L3) и по содержимому (L7)», «Частичная доступность
(белый список)», «Фильтрация протокола VPN». (2) `--why` при TLS-fail: «возможна TLS/SNI-фильтрация»
(было «фильтрация TLS»). ИНВАРИАНТЫ (жёстко): вероятностно («возможна», «похоже»), НЕ «DPI доказан»;
БЕЗ политлексики в выводе (РКН/ТСПУ/госблок — даже не в коде); БЕЗ рецептов обхода (zapret/VLESS/
desync — не наш продукт, fixnet чинит безопасно, не обходит).

СДЕЛАН `whitelist_like` в `--probe` (продолжение 14.1): в ветке, где внешний TCP 443 закрыт
(1.1.1.1/apple), ДОПРОБУЕМ РЕГИОНАЛЬНЫЕ контрольные хосты (ya.ru, vk.com — НЕ «локальные»: локальное
это 192.168/.local/роутер) — если они открываются, а внешние нет → частичная доступность. 🔒 Только
при tcp_base==0 И allow_open≥1: в обычной сети (внешние открыты) ветка спит, ложных нет; региональные
тоже закрыты → честно «общий обрыв»; нет nc → мягко общий. ПОЛИРОВКА по ревью: 2/2 открылись →
«похоже на частичную доступность / белый список», 1/2 → «возможна (слабый признак)»; «белый список»
НЕ как факт (доказан ПАТТЕРН, не механизм); печатаем ОСНОВАНИЕ («контрольные: внешние — нет;
региональные: ya.ru — да; …»); VPN-aware — при VPN_ACTIVE причина может быть в VPN-маршруте/
split-tunnel/политике сервера, а не в провайдере. Грунтанул: ya.ru/vk.com:443 открываются; норм-сеть
→ strong UDP, ветка не трогается.

ПОЛНАЯ ТАКСОНОМИЯ `--probe` (Фаза 14.1, завершено). `probe_report` теперь даёт ОДИН
диагностический тег по дереву решений (строго по фактам, вероятностно) + «Карту проверок»
(прозрачное основание: TCP внешний IP/домен, TLS поверх TCP, UDP-рефлекторы):
  - `tcp_block_like` — внешний TCP 443 закрыт И региональные тоже (общий обрыв/портал/связь);
  - `whitelist_like` — внешний закрыт, региональные открыты (частичная доступность);
  - `dns_block_like` — TCP до IP есть, до домена нет (фильтр/проблема DNS, не сеть);
  - `tls_sni_filter_like` — TCP встаёт, а TLS рвётся на НЕСКОЛЬКИХ доменах (нов. проба `probe_tls`
    по curl-таймингам time_connect/time_appconnect; «возможна TLS/SNI-фильтрация/прокси/инспекция»);
  - `udp_partial` / `udp_restricted` — TLS ок, но UDP частично/совсем не отвечает;
  - `ok` — внешний TCP+TLS+UDP проходят.
`vpn_protocol_restricted_like` — НЕ отдельная проба (handshake VPN не воспроизвести), а ЗАМЕТКА
при udp_partial/udp_restricted: «если OpenVPN/WireGuard по UDP не встаёт — возможна фильтрация
протокола, не доказано». 🔒 TLS-пробы запускаем ТОЛЬКО при живом DNS+TCP до домена (иначе TLS-fail
= это DNS, не SNI). Грунтанул: норм-сеть → карта вся зелёная, класс `ok`; дерево из 7 классов
проверено на mock. ИНВАРИАНТЫ: вероятностно, без политлексики, без рецептов обхода.
СТРАХОВКИ ПЕРЕД ОБКАТКОЙ (правка по ревью — `tls_sni_filter_like` самый опасный класс): «TLS рвётся»

## Фаза 8 (сделано): DoH-фолбэк для DNS — `network_ok ≠ системный DNS жив`

ЦЕЛЬ: отличить «обычный (UDP-53) резолвер молчит, но резолвинг ВОЗМОЖЕН (DoH проходит)»
от «резолвинг не идёт вовсе». Раньше оба сливались в «DNS не работает → fixnet --dns»,
давая ЛОЖНУЮ тревогу, когда система на шифрованном DNS/Private Relay (dig по UDP-53
падает, а браузер резолвит). netinfo-only, read-only.

🔒 ИНВАРИАНТ: DoH-успех НЕ переписываем в «DNS работает». UDP-53 и DoH — РАЗНЫЕ факты.
«UDP-53 молчит» ≠ «имена не резолвятся»; «DoH проходит» ≠ «системный DNS жив»
(приложения могут не использовать DoH). И НЕ маскируем реальную поломку локального DNS,
которую чинит `fixnet --dns`.

ПРОБА (`doh_probe`): ТОЛЬКО если `DNS=0` И есть связь (NET или HTTPS). Не плодим запросы
при живом резолвере. Якоря (двух достаточно): `https://1.1.1.1/dns-query?name=ya.ru&type=A`
(accept: application/dns-json) → фолбэк `https://dns.google/resolve?...`. Успех =
`"Status":0` + `"data"` (непустой Answer), grounded вживую. `DOH_OK`: ""=не проверяли /
1 / 0. С дата-центрового VPN сам DoH может быть зарезан → DOH_OK=0 (честный сигнал
«резолвинг не проходит вовсе», а не «жив»).

ТАБЛИЦА РЕШЕНИЙ (строка «адреса (DNS)» + рекомендация):
  - DNS=1            → как раньше (резолвер жив), DoH не пробуем;
  - DNS=0 DoH=1 сайты✅ → 🟡 «обычный DNS молчит, но имена резолвятся через DoH»; ремонт
    НЕ зовём (ложная тревога убрана). MAIN_OK остаётся 🟢 (HTTPS_OK && (DNS||DOH_OK)),
    но слой DNS жёлтый — верхний вердикт не врёт, и «всё зелено» не рисуем;
  - DNS=0 DoH=1 сайты❌ → 🟡 «обычный DNS не работает; DoH проходит» → `sudo fixnet --dns`
    (переключит сервисный резолвер на 1.1.1.1, должно помочь);
  - DNS=0 DoH=0       → 🔴 «не резолвится ни обычным DNS, ни через DoH» → проблема глубже,
    `fixnet --dns` может не помочь (честная оговорка);
  - DNS=0 DoH=""(нет связи) → как раньше.

JSON: блок `dns: {udp53:bool, doh:true|false|null}` (doh=null если не пробовали). Коды:
`dns_doh_only` (UDP-53 мёртв, DoH жив), `dns_unresolvable` (оба мертвы). Третий код
(`dns_udp53_failed`) сознательно НЕ добавляли — хватает двух.

ЧЕГО НЕ ДЕЛАЕМ: не писать «DNS работает» при живом только DoH; не отменять `fixnet --dns`
там, где сайты НЕ открываются; не пробовать DoH всегда; не добавлять DoH в fixnet как
действие (только диагностика); не лезть в системный DoH-профиль (read-only). Регрессия:
DNS жив → DoH-шума нет; матрица DNS×DoH×HTTPS (4 ветки); doh_probe резолвит вживую;
--json dns-блок+коды валиден. ✅

КОНКРЕТНЫЕ AI-сервисы и с какой задержкой. netinfo-only, read-only, БЕЗ ключей и
промптов; fixnet НЕ участвует (действие — сменить сервер в VPN-клиенте).

ФУНДАМЕНТ + СЕМАНТИЧЕСКАЯ ПРАВКА (важно). ICMP до api.openai.com БЕСПОЛЕЗЕН (CDN с
граничного узла — 71→297 мс). Меряем **TLS-handshake** (`curl -w %{time_appconnect}`).
НО: TLS прошёл ≠ нейросетью можно пользоваться. Из РФ-выхода OpenAI/Claude/Gemini
завершают TLS и даже отвечают HTTP, но это **403 «регион не поддерживается»** —
старая логика «любой HTTP-код = доступен» это ПРОГЛАТЫВАЛА (ложное «доступен»). Код
403 САМ ПО СЕБЕ недостаточен: Gemini ОТДАЁТ 403 и в рабочем регионе (это «нет ключа»,
тело «unregistered callers»). Поэтому читаем ТЕЛО ответа и ищем маркеры блокировки.

ЧЕТЫРЕ КЛАССА (verdict), классификатор `ai_classify` код+тело:
  - `blocked` 🔴 — отказ. ДВЕ ПОДКАТЕГОРИИ (разный диагноз → разное действие):
      • РЕГИОН/политика → «🔴 региональный отказ — смени СТРАНУ VPN»: маркеры
        `unsupported_country*`, «region, or territory not supported», «location is not
        supported», «not available in your country», «request not allowed» (Anthropic
        регион-отказ, заземлён вживую: из РФ 403 «Request not allowed», в рабочем
        регионе 405), код 451, ИЛИ «голый» 403 (forbidden без «нужен ключ»);
      • ANTI-BOT/репутация IP → «🔴 антибот-защита (IP в чёрном списке) — смени
        СЕРВЕР/IP, лучше не дата-центр»: маркеры «just a moment», «attention required»,
        «checking your browser», «error code: 1020», «you have been blocked», «access
        denied». Это про репутацию IP VPN-дата-центра (EDIS/Gigahost/UFO…), НЕ про
        страну — потому действие другое. reason: cloudflare_antibot/cloudflare_1020/
        blocked_page/access_denied;
    (forbidden без объяснения «нужен ключ»);
  - `unconfirmed` 🟡 — 403 С фразой «нужен ключ» (`api key`/`unregistered callers`/
    `authenticat`/`permission_denied`): без ключа НЕ отличить блок от нет-ключа;
  - `network_ok` 🟢 — обычный ответ (401/405/400/429/200): сеть прошла, не forbidden.
    Грейд по TLS: good ≤400 / degraded 400–800 / slow >800;
  - `unreachable` 🔴 — code=000/таймаут/TLS-fail.
ПОРЯДОК В КЛАССИФИКАТОРЕ ВАЖЕН: региональные маркеры ДО проверки «нужен ключ» (Google-
регион тоже PERMISSION_DENIED, но с текстом про location — это блок, не «нет ключа»).
`network_reachable=true` И `verdict=blocked/unconfirmed` НЕ противоречат: сеть дошла →
сервер отказал/не подтвердил.

🔴 ЖИВОЙ КЕЙС РФ (зачем 4-й класс). С RU-выхода OpenAI/Claude/Gemini вернули 403, но
старая логика «тело без маркера → network_ok» проглатывала Claude и Gemini (показывала
🟢 «сеть проходит» — а они НЕ работали). Разбор: (1) Claude в рабочем регионе отвечает
405, а 403 для него — аномалия → «голый» 403 = `blocked` ловит его надёжно; (2) Gemini
отдаёт 403 «нужен API-ключ» БЕЗ ключа и в рабочем регионе, и из РФ — ответы одинаковы,
поэтому keyless отличить блок от нет-ключа НЕВОЗМОЖНО → честно `unconfirmed` 🟡 в любом
регионе (подтвердит лишь будущий `--ai-auth` с ключом). Выбор владельца: 🟡 честно «не
подтверждён», НЕ ложный зелёный и НЕ ложный красный.

ТЕРМИНОЛОГИЯ (НЕ откатывать): в безключевом блоке пишем «сеть проходит», НЕ «доступен»
(чтобы не обещать рабочую модель); блок — «региональный отказ» / «отклонён по региону
или политике», НЕ «РКН/DPI/госблок» (по телу видим лишь отказ сервиса/CDN/политики,
не источник). Заголовок блока — «AI API-домены».

🔒 ИНВАРИАНТ ФОРМУЛИРОВОК (зафиксирован, НЕ нарушать). В AI-блоке БЕЗ ключей ЗАПРЕЩЕНО
писать: «нейросеть доступна», «модель работает», «OpenAI работает» (мы этого не
проверяли — нет ни ключа, ни запроса к модели). РАЗРЕШЕНО: «API-домен отвечает», «сеть
проходит», «региональный отказ», «не достучались». Причина: без ключа мы доказываем
лишь сетевую достижимость домена и факт отказа/ответа, а НЕ продуктовый доступ к модели.
`--ai-auth` (с ключами/моделями/лимитами) — ОТДЕЛЬНАЯ будущая фаза (там появятся
секреты, стоимость, риск реальных запросов); в текущую безключевую фазу НЕ тащить.

КОМАНДЫ: `--ai` (дефолт OpenAI+Claude), `--ai all` (+Gemini+Z.AI), `--ai list`,
`--no-ai`. Клавиша `i` в меню = ПОЛНЫЙ набор (`--ai all`); обычный вывод/`r` — базовый
(collect_all форсит AI_MODE=default). Блок в основном выводе — по умолчанию при
активном VPN (опт-аут `--no-ai`); без VPN не шумим; `--ai` — всегда.

ЧТЕНИЕ ТЕЛА: ai_check делает ОДИН `curl -L -o <tmp> -w '%{http_code}\t%{time_appconnect}
\t%{time_namelookup}'`, тело анализируем `head -c 8192 | tr A-Z a-z`. Тело в логи/JSON
НЕ кладём — только классификацию (verdict, block_reason, http_code). TSV-поля (10):
name host net code latency_ms dns_ms verdict grade block_reason err — пустые поля
сентинелом «-» (иначе подряд табы схлопнулись бы в read; урок --scan).

WORK при активном VPN + AI-проверке: «не работает» = blocked ИЛИ unreachable. Все ок →
«AI API-домены отвечают (имена)»; все плохо и все blocked → «отклоняют доступ из этого
региона — смени страну VPN»; все плохо иначе → «недоступны через текущий сервер»;
часть → «но <имена> отклонены/недоступны — смени страну VPN».

КОНФИГ — только ДАННЫЕ, НИКОГДА `source`/eval: `~/Library/Application Support/netinfo/
ai-targets`, `Имя<TAB>URL`. Пусто/`#` → пропуск; только `https://` (иначе предупреждение);
имя clean(); dedupe по имени.

JSON: блок `ai[]` только если проверка запускалась. Поля: name, url_host (НЕ полный URL),
**network_reachable** (TLS/HTTP дошёл), http_code (null если 000), latency_ms (null если
unreachable), dns_ms, **verdict**(network_ok|blocked|unconfirmed|unreachable), **block_reason**
(код причины / `needs_key` для unconfirmed / null), error. Consumer смотрит `verdict`,
НЕ только network_reachable. Коды: `ai_checked`, `ai_region_blocked` (все blocked),
`ai_partial_blocked` (часть blocked), `ai_unconfirmed` (есть unconfirmed),
`ai_unreachable` (все unreachable), `ai_high_latency` (есть network_ok с latency>400).

ЧЕСТНЫЕ ОГОВОРКИ (в --ai/docs): «сеть проходит = API-домен ответил без явных признаков
регионального отказа; НЕ проверка ключа, не запрос к модели, не гарантия скорости».
time_appconnect — нижняя оценка. ОСТАТОЧНЫЙ РИСК: блок с НЕизвестной фразой в теле
проскочит как network_ok (маркеры пополняемы) — честно отмечено.

РЕАЛИЗАЦИЯ: последовательно; таймаут ОБЯЗАТЕЛЕН (`--connect-timeout 5 --max-time 8`).
ai_build_targets → ai_check (читает тело) → ai_summarize → ai_render (compact/detail).
🔴 ГРАБЛИ: `ai_render` под `set -u` падал на необъявленном `$2` → `${2:-}`. Регрессия
вживую: network_ok 🟢 (OpenAI 401/Claude 405 «сеть проходит»); unit-тест ai_block_reason
(Gemini-403-nokey → network_ok, unsupported_country/1020/451 → blocked); живой blocked

## Фаза 5 (сделано): `netinfo --probe` — проба TCP/UDP-выхода для VPN

НЕ «детектор DPI/шейпинга» (это было бы самоуверенно — мы НЕ диагностируем DPI и
НЕ меряем шейпинг скорости: для шейпинга нужен endpoint, говорящий на протоколе
VPN, которого у нас нет). Это **проба сетевых ОГРАНИЧЕНИЙ выхода**: что доказуемо
открыто/закрыто и пригодна ли сеть для UDP-VPN. Заголовок в выводе — «Проверка
ограничений TCP/UDP для VPN».

ФУНДАМЕНТ ЧЕСТНОСТИ (главное; ради этого фаза и делалась осторожно): **TCP-connect
доказуем** (open/closed/refused — факт), **UDP — НЕТ** (нет ответа ≠ блок: может
быть нет слушателя, сервер игнорит мусор, stateful-фильтр молча роняет, rate-limit,
потеря). Поэтому UDP меряем ТОЛЬКО через рефлекторы, ОБЯЗАННЫЕ ответить, и выводы
делаем по ним с «похоже / скорее всего».

- **netinfo-only**: read-only, без root, НЕ пишет state, **fixnet НЕ участвует**
  (от ограничений UDP нет безопасного локального «ремонта» — действие в VPN-клиенте:
  сменить протокол/сервер). Флаг `netinfo --probe` (медленный — UDP-таймауты; в
  обычный вывод НЕ тащим, как `--mtu`).
- **Что меряем** (всё grounded вживую): TCP baseline `nc -G2 -z 1.1.1.1 443` (IP без
  DNS) + `nc www.apple.com 443` (с DNS — для развязки «DNS vs сеть»). UDP-рефлекторы:
  53/DNS (`dig @1.1.1.1`), 123/NTP (`sntp`, якоря apple→google), 3478/STUN (python3,
  cloudflare→google:19302, ≤2 c/якорь). `/dev/tcp` в системном bash 3.2 НЕдоступен —
  только `nc`.
- **Весовая логика UDP** (STUN — лучший прокси произвольного UDP, потому весомее):
  STRONG = STUN ответил ИЛИ ≥2 из {DNS,NTP,STUN}; PARTIAL = только DNS ИЛИ только NTP;
  BAD = TCP жив, но весь UDP молчит. Один NTP-таймаут при живом STUN не топит вердикт.
- **Формулировки** (правка-инвариант, НЕ ослаблять): НЕ «WireGuard/OpenVPN должны
  проходить», а 🟢 «Общий UDP-выход работает. Полной блокировки UDP не видно. Если
  конкретный VPN всё равно не работает — возможна точечная блокировка порта/протокола,
  MTU или проблема сервера (это отсюда не доказывается)». PARTIAL/BAD → 🟡 «попробуй
  VPN через TCP 443 / Lightway TCP / OpenVPN TCP». UDP-факты пишем «отвечает / не
  ответил / не проверено», НЕ «заблокирован».
- **СОЗНАТЕЛЬНО НЕ делаем**: (1) НЕ стучим пустыми UDP в 1194/51820/500/4500 —
  молчание недоказуемо; (2) НЕ называем конкретный порт VPN «заблокированным»
  (точечную блокировку именно порта отсюда НЕ видно — это прямо оговорено в выводе);
  (3) НЕ пишем «DPI доказан»; (4) НЕ диагностируем подмену DNS (UDP53 = «ответ
  получен», не «DNS без подмены»); (5) проверку КОНКРЕТНЫХ VPN-эндпоинтов из конфига
  ОТЛОЖИЛИ (нужны реальные host:port, для UDP всё равно нет честного ответа без
  handshake, появляются секреты — ядро должно быть без персональных endpoint'ов).
- TCP 443 закрыт к обоим якорям → выход с «это про связь/портал/локальную фильтрацию,
  не про DPI». IP открыт, домен нет → замечание «похоже на DNS, не сеть».
- Указатель на `--probe`: в `--advice` КОНТЕКСТНО (только VPN_ACTIVE ИЛИ SEC_OPEN),
  в `--tech` строкой; в обычном выводе НЕТ. В меню кнопки не добавляли (как `--mtu`).
- Регрессия пройдена: п.1 нормальная сеть → 🟢; ярусы STRONG/PARTIAL/BAD; skip-рендер
  «не проверено» без nc/python3; запрет слов «заблокирован/DPI» в коде; `--probe` нет
  в обычном выводе; пайп чистый (спиннер в /dev/tty). ✅

## Фаза 4 (сделано): MTU path discovery — `netinfo --mtu` + `fixnet --mtu`

PMTU-blackhole: сеть молча режет крупные DF-пакеты (path MTU < MTU интерфейса) →
пинг/лёгкие сайты идут, а VPN/TLS/тяжёлый контент зависают. Сверено вживую:
интерфейс 1500, а path MTU до 1.1.1.1 и 8.8.8.8 = 1492 (payload 1464 проходит, 1472 нет).
- Зонд (netlib `nl_path_mtu`): бинарный поиск макс DF-payload через `ping -D -s`
  (без root; IPv4 ICMP: packet = payload+28), МИНИМУМ по якорям 1.1.1.1/8.8.8.8,
  провал перепроверяется 1 раз. Малый зонд не прошёл → «не удалось измерить» (НЕ
  «ICMP заблокирован» как факт). Якоря 1.1.1.1+8.8.8.8 — те же PROBE_IP.
- `netinfo --mtu` — read-only: отдельный флаг (зонд медленный, в обычный вывод НЕ
  тащим; в --tech строка «MTU интерфейса: N (проверить: netinfo --mtu)»). Порог
  рекомендации: iface−path ≥8 б → рекомендуем `sudo fixnet --mtu` (мягко); 1–7 б —
  «менять не рекомендую»; >40 б — «выраженное». Оговорка: путь до VPN-сервера может
  отличаться; при full-tunnel VPN мерится путь туннеля.
- `fixnet --mtu [N]`: persistent `networksetup -setMTU <device> <target>` с бэкапом/
  откатом/self-heal/guard КАК У DNS. target = N или измеренный путь; валидация
  1280≤target≤1500 И target<current (иначе «менять нечего»). Подтверждение [y/N]
  ВСЕГДА дефолт N (persistent-мутация); при full-tunnel VPN — доп. предупреждение
  «смена MTU физического en0 может не помочь». После setMTU проверяем getMTU (принял
  ли) + DF-пакет target−28 + check_net. Бэкап `mtu-backup/active.json` (schema:1:
  device/old_mtu/new_mtu/path_mtu). Откат: `setMTU device old_mtu` (режим один —
  число, нет empty как у DNS). Команды: `--mtu`, `--mtu-restore`, `--mtu-status`.
- self-heal MTU осторожный: если MTU изменён вручную (≠ new_mtu) → superseded, ручное
  НЕ трогаем (не «улучшаем» до измеренного, не возвращаем 1500).
- ⚠ напоминание: после тестов вернуть MTU (`sudo fixnet --mtu-restore` или
  `sudo networksetup -setMTU en0 1500`).

## Фаза 3 (сделано): `fixnet --wifi-reset` — залипшая Wi-Fi-сессия

Контракт: netinfo ДИАГНОСТИРУЕТ «похоже, сессия залипла» и рекомендует
`sudo fixnet --wifi-reset`. Передёргивает радио только fixnet.
- Команды: `fixnet --wifi-reset` (алиас `--reassoc`): off→sleep3→on→sleep2→`ipconfig
  set DHCP`→`wait_net 30`→`sleep 4` (дать каналу устаканиться — сразу после off/on
  RTT в переходном состоянии, видели всплеск 23→211 мс на здоровой сети).
  ДЕСТРУКТИВНО (рвёт все соединения) → подтверждение
  дефолт **N**; `--yes` намеренно НЕ действует (только осознанный интерактив; без
  TTY — отмена). Бэкап/откат НЕ нужны (действие самовосстановимо). Tailscale/VPN
  не трогаем — туннели переподключатся сами.
- Проверка управляемости: `is_wifi` (т.е. `networksetup -getairportpower`) — не
  только «это enX»; не-Wi-Fi (кабель/USB) → отказ.
- Снимок ДО/ПОСЛЕ (wr_snapshot: net/dns/RTT_avg/loss) и ЧЕСТНОЕ сравнение:
  «помогло» (вернулась достижимость / потери −50% / RTT −30% и сейчас всё ок),
  «стало немного лучше, но не ушло», «не помогло (дело не в Wi-Fi)», «стало хуже».
- НЕ пишем историю/ops в state (Фаза 3 проще; позже можно).
- ТРИГГЕР в netinfo (STUCK) СТРОГИЙ, чтобы не путать с «узким местом»: WIFI=1,
  CAPTIVE=0, радио хорошее (RSSI≥-67 ИЛИ SNR≥30 — только под root), И сильная
  нестабильность: loss≥10% ИЛИ RTT_avg>250 ИЛИ jitter>150 ИЛИ RTT_max>800.
  При одной низкой скорости (RTT/потери ОК) → НЕ рекомендуем (это «узкое место»).
- ФОРМУЛИРОВКА осторожная: «связь наружу нестабильна» (потери на внешнем ping НЕ
  доказывают, что кадры падают на самом Wi-Fi — может быть провайдер/хотспот/VPN);
  «иногда помогает передёрнуть», не «починит». RTT шлюза как критерий НЕ берём.
- Меню `w` в netinfo НЕ добавляли (как и `d` для DNS) — на первом проходе только
  текстовая рекомендация, чтобы пользователь раз явно увидел подтверждение/итог.

## Фаза 2 (сделано): `fixnet --dns` — первый «ремонтный» сценарий

Контракт: netinfo только ДИАГНОСТИРУЕТ «DNS мёртв» и печатает `sudo fixnet --dns`
(без меню `d` на первом проходе — пусть пользователь раз явно увидит бэкап/откат).
Меняет DNS ТОЛЬКО fixnet.
- Команды: `fixnet --dns` (бэкап → 1.1.1.1/8.8.8.8 → flush → проверка),
  `--dns-restore`, `--dns-status` (read-only), `--dns --yes` (неинтерактивно).
- `netlib.sh` для fixnet ОБЯЗАТЕЛЕН (нет — отказ; ремонт без отката запрещён),
  в отличие от netinfo (мягкая деградация).
- Бэкап `dns-backup/active.json` (schema:1): service/device/old_dns_mode(manual|
  empty)/old_dns/new_dns/status. Откат: empty → `setdnsservers Empty`, manual →
  список. Журнал `dns-ops.jsonl` (applied/restored/superseded).
- ИСТОЧНИК DNS для бэкапа/проверки — `networksetup -getdnsservers <service>` (конфиг
  сервиса), НЕ `scutil` (тот показывает эффективные резолверы, вкл. Tailscale).
  Проверка «закрепился ли» — тоже через networksetup; то, что scutil при Tailscale
  продолжает показывать 100.100.100.100 — это НЕ провал (сервисный DNS стал upstream).
- SELF-HEAL важнее trap: в начале ЛЮБОГО запуска fixnet — если есть забытый
  active.json и DNS всё ещё наш → предложить вернуть; если DNS уже другой → пометить
  superseded и убрать. trap не спасает от SIGKILL/ребута — гарантия в файле+self-heal.
- TAILSCALE (у владельца почти всегда активен): НЕ блокируем ремонт. Сообщение
  ИНФОРМАЦИОННОЕ (дефолт Y): «меняю DNS сервиса как upstream; tailnet/MagicDNS обычно
  не затрагиваются (но fixnet не управляет режимами Tailscale)». Если DNS не
  закрепился (Tailscale пере-навязал) — честно сообщаем, tailscale CLI не трогаем.
- service_for_device (netlib): networksetup работает с именем сервиса «Wi-Fi», а не
  «en0». Сверено: getdnsservers(Wi-Fi)=192.168.5.1, а scutil=100.100.100.100 — норма.
- Сервисный DNS-ремонт (--dns, замена серверов) ≠ старый `vpndns` (мягкий рестарт
  mDNSResponder при «интернет есть, но резолвер завис») — оба сосуществуют.
- ГРАБЛИ повторного --dns: если подмена в силе, второй --dns НЕ делает новый бэкап
  (иначе old_dns перезаписался бы на 1.1.1.1 и оригинал потерялся) → отказ «верни
  через --dns-restore». «Вернуть?» спрашивает только обычный fixnet/self-heal, не --dns.
- Регрессия Фазы 2 пройдена ВЖИВУЮ: guard, restore (оригинал сохранён), C/empty→DHCP,
  D/self-heal (Y возвращает), E/superseded (ручной 9.9.9.9 не перетёрт). ✅

## Фаза 1 (сделано): память + узнавание + заход в портал

- Слой состояния `netlib.sh` (функции nl_*). STATE_DIR =
  `~/Library/Application Support/netinfo/` (history.jsonl, config; позже dns-backup).
- ГЛАВНАЯ ЛОВУШКА — sudo: кнопка зовёт `sudo netinfo.sh`, и `$HOME` становится
  /var/root. Реального пользователя берём из `SUDO_USER` (nl_real_user/real_home
  через dscl), после записи под root делаем `chown -R "$SUDO_USER":staff STATE_DIR`,
  иначе обычный запуск не прочитает свою же историю.
- История JSONL, `schema:1`, лимит 1000 строк (tail). Включена ПО УМОЛЧАНИЮ,
  только локально, наружу не отправляется. Очистка: `--forget` (спросит [y/N];
  `--yes` без вопроса). Разово без записи: `--no-history`. Тумблер: `--history
  on|off|status`. Путь: `--state`, открыть в Finder: `--open-state`.
- Пишем историю ТОЛЬКО в collect_all (первый замер и `r`); t/a не пишут. Узнавание
  («Память: были тут N раз; прошлый раз — <вердикт>») читаем ДО записи текущего.
  Причину прошлого визита реконструируем из сохранённых полей (честно, не выдумка).
- Captive: достаём URL портала из Location, в меню пункт `o` — открыть в браузере
  В СЕССИИ ПОЛЬЗОВАТЕЛЯ (`sudo -u "$SUDO_USER" open`), не от root. Это не мутация
  сети, поэтому допустимо в netinfo.
- 🔴 ГРАБЛИ (стоили часа): имя переменной `HISTCMD` — ВСТРОЕННАЯ спец-переменная
  bash (номер команды в истории). Коллизия давала «1»/«unbound variable» в самых
  невинных местах. Переименовано в HIST_CMD. Урок: не использовать имена bash-
  спецпеременных (HISTCMD, SECONDS, RANDOM, LINENO, PIPESTATUS, ...).
- macOS bash = 3.2: разбор флагов на while/shift; избегать редких конструкций.
- NAMESPACE (правило по ревью): nl_* — netlib, NI_* — netinfo/fixnet; не брать имена
  спецпеременных bash. Зафиксировано в шапке netlib.sh.
- «Память» СПОКОЙНАЯ (правка по ревью): в обычном выводе без 🔴-драмы — один
  тестовый всплеск не должен пугать «прошлый раз плохо». Если прошлый визит «только
  что» — нейтрально «прошлый замер был только что»; иначе «было нормально / были
  замечания». Точные цифры — в history.jsonl (и в будущем --tech). НЕ возвращать
  драматичный вердикт прошлого визита в обычный вывод.
- `--state` показывает путь · история · число записей · владелец (для отладки
  после запуска кнопкой под sudo). Чек-лист регрессии Фазы 1 (10 пунктов) пройден;
  п.10 (владелец $SUDO_USER:staff после кнопки-sudo) проверяется вживую на кнопке.

## Что скрипт СОЗНАТЕЛЬНО НЕ делает (не предлагать!)

- НЕ делает глобальный `route flush -inet6` — это рвёт рабочую IPv6 и активный
  VPN. Был в ранней версии, убран как самый опасный элемент. Только прицельное
  удаление дефолтов на utun.
- НЕ убивает VPN-клиенты и НЕ выгружает NetworkExtension.
- НЕ удаляет сами utun-интерфейсы (нельзя безопасно выгрузить чужой VPN на лету).
- НЕ меняет DNS-серверы В ОБЫЧНОМ ремонте (route/DHCP). DNS-серверы меняет ТОЛЬКО
  явный режим `fixnet --dns` — с бэкапом и откатом (Фаза 2, см. ниже).
- НЕ трогает Tailscale: не вызывает `tailscale` CLI, его настройки не меняет (даже
  в `--dns` — только DNS сервиса ОС).
- НЕ читает DNS через dscacheutil как основную проверку (кэш врёт — это и был
  баг, из-за которого «помогала только перезагрузка»).

## История ревью (10 раундов)

Прошёл 10 кругов внешней критики. Ключевые уроки:
- глобальный flush IPv6 опасен -> убран;
- check_dns должен мерить живой резолв, а не кэш (вскрыто боевым тестом:
  ERR_NAME_NOT_RESOLVED при живом пинге);
- случайный поддомен в проверке DNS = инверсия (NXDOMAIN доказывает, что
  резолвер жив, а не сломан) -> проверяем реальные имена;
- locate_break должен влиять на решение, а не украшать вывод;
- detect_iface: факт (default route) важнее имени сервиса;
- комментарии объясняют ПОЧЕМУ, а не ЧТО (для себя через год).

## Журнал запусков fixnet + синхронизация ~/bin (deploy.sh) — инфраструктура

ЖУРНАЛ (always-on, netlib-путь). Каждый запуск fixnet пишет отдельный файл в
`$(nl_state_dir)/fixnet-logs/` (= `~/Library/Application Support/netinfo/fixnet-logs/`; владелец —
РЕАЛЬНЫЙ пользователь через nl_chown_state, не root под sudo). Внутри: весь вывод (tee) + СЫРЫЕ
снимки сети ДО и ПОСЛЕ (`route get default`, `netstat -rn` v4/v6, `ifconfig`, `scutil --dns`) —
для разбора инцидентов постфактум («что было с маршрутами/DNS, что стало»). Ротация — 30 последних.
🔒 ИНВАРИАНТЫ (не нарушать): (1) снимок «после» встроен в ЕДИНЫЙ `cleanup()`, а НЕ отдельным
`trap raw_snapshot EXIT` (иначе перетёр бы cleanup спиннера — bash-trap заменяет, не копит); (2)
снимок пишется НАПРЯМУЮ в файл (минуя tee) — финальный «после» ляжет даже при гонке на выходе; (3)
сбой журнала (нет каталога/tee) НЕ роняет ремонт — FIXNET_LOG="" и всё работает как раньше. ⚠
ПОБОЧНЫЙ ЭФФЕКТ tee: `exec > >(tee)` делает stdout не-tty → `nl_spin_ok` (`-t 1`) выключает braille-
спиннер; но на длинных операциях есть текстовый фолбэк (`[ -t 1 ] || echo …` на MTU-зонде/wait_net),
а подтверждения читаются со stdin (`-t 0`) и tee их НЕ трогает. Осознанный размен: полный журнал
важнее анимации. НЕ добавлять журнал в netinfo (read-only; у него своя history.jsonl) — только fixnet.

СИНХРОНИЗАЦИЯ (`deploy.sh`). 🔴 ИНЦИДЕНТ-УРОК: канон живёт в репо (`~/projects/fixnet`), а кнопки
зовут `~/bin/*.sh`. Однажды `~/bin/fixnet.sh` отстал на ~500 строк (потерял весь DNS-ремонт), потому
что синхронизация держалась «на памяти», а прошлая правка ЖУРНАЛА писалась ПОВЕРХ устаревшей ~/bin-
копии и залилась в репо, затерев Фазу 15.0 (спас «случайный» revert). ПРАВИЛО: после правок канона
ВСЕГДА `./deploy.sh` (netlib/fixnet/netinfo/access → ~/bin, с шебанг- и `bash -n`-проверкой, копирует
лишь отличающееся; `./deploy.sh --check` — сухой прогон). НЕ редактировать `~/bin/*.sh` напрямую и НЕ
копировать из ~/bin в репо — источник правды только репо. Иконизированные .command по-прежнему
обновляются `cat >` (deploy их НЕ трогает — только .sh).

## Установка / использование

Рабочая копия живёт в `~/bin/fixnet.sh`, кнопка `~/bin/fixnet.command` (и копия
на рабочем столе / в Dock) запускает её. Этот репозиторий — канонический исходник.
После правок: `cp fixnet.sh ~/bin/fixnet.sh && chmod +x ~/bin/fixnet.sh`.
Диагностика-companion: `cp netinfo.sh ~/bin/netinfo.sh && chmod +x ~/bin/netinfo.sh`,
запуск `netinfo.sh` / `--tech` / `--advice` / `--no-speed` / `--no-geo`.
Короткая команда `netinfo` — симлинк `ln -sf ~/bin/netinfo.sh ~/bin/netinfo` (чтобы
подсказка `netinfo --tech` работала в терминале; скрипт не зависит от $0).
Кнопка после осмотра предлагает меню без терминала: `t` — `--tech`, `a` — `--advice`
(пароль sudo закэширован первым запуском, повторно не спрашивает).
Кнопка осмотра живёт на рабочем столе (`~/Desktop/netinfo.command`, зовёт
`~/bin/netinfo.sh`). Иконка — в стиле fixnet (тёмный фон + зелёные дуги Wi-Fi),
но с ЛУПОЙ вместо молнии. Исходник иконки воспроизводим: `make-netinfo-icon.py`
(PIL) -> `netinfo_1024.png` -> `iconutil` -> `netinfo.icns`; навешивается на
.command через `NSWorkspace setIcon:forFile:` (osascript, без сторонних утилит).
ВАЖНО (грабли): одного setIcon мало — он пишет resource fork с картинкой, но НЕ
ставит флаг кастомной иконки в FinderInfo, и Finder её игнорирует. Нужен ещё
`SetFile -a C <file>` (или записать FinderInfo: байт 8 = 0x04) + `killall Finder`.
Если setIcon упёрся в кэш icon services — надёжный ручной путь: PNG в буфер
(`osascript ... read ... as «class PNGf»`) -> Cmd-I на файле -> клик по иконке
вверху слева -> Cmd-V.
Чтобы в имени не было «.command» (как у синих кнопок) — флаг скрытия расширения:
`SetFile -a E <file>` (файл остаётся .command и кликабельным, прячется только
показ расширения; работает, пока в Finder не включено «показывать все расширения»).
ОБНОВЛЕНИЕ иконизированной кнопки — ТОЛЬКО через `cat new.command > ~/Desktop/...`
(перезаписывает данные, сохраняя resource fork и флаги C/E). `cp` допустим лишь
при ПЕРВИЧНОЙ установке — повторный `cp` снесёт иконку и скрытие расширения.

Проверка: `./fixnet.sh --check` (без root). Починка: `sudo ./fixnet.sh`.
